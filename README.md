FHIR R4 on Supabase, ready to clone. Postgres schema, row level security per patient, audit log,
version history and a FHIR-flavoured API, seeded with synthetic patients from Synthea.
Postgres first: the rules live in the database, so any language talks to it over HTTP or SQL.

[![ci](https://github.com/eudanielvieira/supabase-fhir/actions/workflows/ci.yml/badge.svg)](https://github.com/eudanielvieira/supabase-fhir/actions/workflows/ci.yml)
[![license: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Every healthcare product on Supabase starts by rebuilding the same foundation: how to store FHIR
resources in Postgres, how to make sure a patient only sees their own data, how to prove who changed
what and who read it. This repository is that foundation, written once, tested, and free to copy.

> Synthetic data only. Every patient in this repository was generated by
> [Synthea](https://synthea.mitre.org). There is no real patient data here and there never will be.

## What you get

| Piece | Where | What it does |
|---|---|---|
| Schema | `supabase/migrations/` | One table per resource type (`fhir.patient`, `fhir.observation`, ...): the full resource as JSONB plus indexed search columns |
| Access control | `fhir.patient_access` and RLS policies | A user sees only the patient compartments they were granted. Admins see everything. Anonymous sees nothing |
| Audit log | `fhir.audit_log` | Every create, update, delete and access grant change, plus every read and search made through the FHIR operations: who, when, which resource, which patient, from where |
| History | `fhir.resource_history` | Every prior version of every resource, FHIR `_history` style |
| FHIR operations | `fhir.*` RPC functions | read, search, create, update with optimistic locking, delete, history, Patient `$everything`, Bundle import. Errors are FHIR `OperationOutcome` |
| HTTP contract | [`docs/api.md`](docs/api.md) | Every call as `curl`, plus the OpenAPI document PostgREST serves. Works from any language |
| Clients | `packages/typescript/`, `examples/` | A typed TypeScript client, NestJS and Elysia backends that forward the user JWT, and dependency-free Go, Python, PHP, Java, C# and Ruby examples |
| Plain Postgres | `sql/compat/`, `sql/dist/` | Run it without Supabase: a compatibility layer and the schema as one file |
| Synthetic data | `supabase/seeds/` | 4 Synthea patients with 500+ resources, the providers they reference, and 3 demo logins |
| Tests | `supabase/tests/`, `tests/http/`, `packages/typescript/tests/` | 129 pgTAP assertions, an HTTP contract suite through PostgREST, every example run against the stack, unit tests for the client |

## Use cases

What the starter is built to do, in plain words. The full list with priorities, and the decisions behind the design, live in
[docs/design](docs/design).

- A developer provisions a FHIR-ready database with one `supabase db reset` and adds resource types with one SQL call.
- A patient signs in and sees their own record and nothing else, enforced by the database.
- A clinician reads and writes the patients they were granted, for as long as the grant is valid.
- An admin grants and revokes access (every change audited), reads the audit log, maintains reference data and is the only one who can delete a Patient.
- A compliance reviewer answers "who touched this patient and when" from `fhir.audit_log` and `fhir.history()`.
- A backend imports FHIR Bundles from Synthea or an EHR with references resolved and the import idempotent.
- Any app, in any language, uses the same HTTP contract: TypeScript, Go, Python, PHP, Java, C#, Ruby, or a client generated from OpenAPI.
- A backend (NestJS, Elysia or any framework) forwards the user JWT and lets the database enforce access instead of holding the service role key.

## Quickstart

Needs Docker and [Bun](https://bun.sh). Node 20 with npm works too: replace `bun` with `npm` and `npx`.

```bash
git clone https://github.com/eudanielvieira/supabase-fhir.git
cd supabase-fhir
bun install
bun run db:start      # starts Supabase locally, applies migrations and seeds
```

`db:start` prints the API URL, the anon key and the service role key. Open Studio at
http://127.0.0.1:54323, pick the `fhir` schema and the seeded patients are there.

Demo logins (local only, password `supabase-fhir` for all three):

| Email | Role | Sees |
|---|---|---|
| `patient@example.com` | patient | their own record and nothing else |
| `clinician@example.com` | clinician | the four seeded patients, read and write |
| `admin@example.com` | admin | everything, including the audit log |

Then pick a language.

**curl** (the contract everything else is built on, see [docs/api.md](docs/api.md)):

```bash
JWT=$(curl -s "$SUPABASE_URL/auth/v1/token?grant_type=password" -H "apikey: $SUPABASE_ANON_KEY" \
  -H "Content-Type: application/json" -d '{"email":"clinician@example.com","password":"supabase-fhir"}' | jq -r .access_token)

curl -s "$SUPABASE_URL/rest/v1/patient?select=id,family_name,birth_date" \
  -H "apikey: $SUPABASE_ANON_KEY" -H "Authorization: Bearer $JWT" -H "Accept-Profile: fhir"

curl -s "$SUPABASE_URL/rest/v1/rpc/read_resource" -H "Content-Profile: fhir" -H "Content-Type: application/json" \
  -H "apikey: $SUPABASE_ANON_KEY" -H "Authorization: Bearer $JWT" -d '{"resource_type":"Patient","id":"<id>"}'
```

**TypeScript** (`packages/typescript/`):

```ts
import { createClient } from '@supabase/supabase-js';
import { createFhirClient, type Database } from './packages/typescript/src';

const supabase = createClient<Database>(process.env.SUPABASE_URL!, process.env.SUPABASE_ANON_KEY!);
await supabase.auth.signInWithPassword({ email: 'clinician@example.com', password: 'supabase-fhir' });

const fhir = createFhirClient(supabase);
const patients = await fhir.search('Patient');                      // only the ones this user may see
const patient = await fhir.read('Patient', patients[0]!.id!);       // audited read
const vitals = await fhir.search('Observation', { patientId: patient.id!, where: { category_code: 'vital-signs' }, limit: 20 });
const bundle = await fhir.everything(patient.id!);                  // Patient $everything
```

**A backend in front of it**: [examples/nestjs](examples/nestjs) and [examples/elysia](examples/elysia)
forward the caller's JWT, so RLS runs as the end user and the API never holds the service role key.

**Go, Python, PHP, Java, C#, Ruby**: `bun run example:go` (or `example:python`, `example:php`,
`example:java`, `example:csharp`, `example:ruby`). Each fits on one screen and uses the standard
library of its language (Java adds Jackson for JSON). See [examples/](examples).

**Anything else**: generate a client from the OpenAPI document PostgREST serves, or call the
RPCs from SQL. Both are in [docs/api.md](docs/api.md).

## Is this a library?

No, and that is the point. The product is the database: migrations you apply to Supabase (or to
any Postgres with the compatibility layer) and an HTTP contract any language can use. The
TypeScript client is one adapter among others and may become an npm package later. See
[Use it in your project](#use-it-in-your-project).

## How data is stored

Every resource type gets its own table with the same shape, created by one function:

```sql
select fhir.define_resource('Specimen');          -- scoped to a patient (default)
select fhir.define_resource('Substance', false);  -- reference data, readable by every signed-in user
```

| Column | Type | Meaning |
|---|---|---|
| `id` | text | The FHIR id. A UUID by default; an id you provide is kept |
| `version_id` | integer | Starts at 1, plus one on every update |
| `last_updated` | timestamptz | Set on every write |
| `resource` | jsonb | The complete FHIR resource. `id`, `meta.versionId` and `meta.lastUpdated` are kept in sync for you |
| `patient_id` | text, generated | The Patient compartment, taken from `subject`, `patient`, `beneficiary` or a Patient `target`. RLS keys on it |
| `created_at`, `created_by`, `updated_by` | | When and by whom (`auth.uid()`) |

Generated search columns cover the common FHIR search parameters, so filters stay in SQL and hit an index:

| Table | Search columns |
|---|---|
| `patient` | `family_name`, `birth_date`, `gender`, `active` |
| `encounter` | `status`, `class_code`, `type_code`, `period_start`, `period_end` |
| `condition` | `clinical_status`, `verification_status`, `code`, `code_system`, `onset_at`, `abatement_at`, `encounter_id` |
| `observation` | `status`, `category_code`, `code`, `code_system`, `effective_at`, `value_quantity`, `value_unit`, `encounter_id` |
| `procedure`, `immunization`, `diagnostic_report`, `medication_request`, and others | see `supabase/migrations/*_fhir_resources.sql` |

```sql
-- blood pressure readings for one patient since 2024
select resource
from fhir.observation
where patient_id = $1 and code = '85354-9' and effective_at >= '2024-01-01';
```

Anything else is a JSONB query with a GIN index behind it:

```sql
select id from fhir.patient
where resource @> '{"identifier":[{"system":"http://hl7.org/fhir/sid/us-ssn"}]}';
```

Shipped resource types (26): Patient, Practitioner, PractitionerRole, Organization, Location,
Medication, Encounter, Condition, Observation, Procedure, MedicationRequest, MedicationAdministration,
Immunization, AllergyIntolerance, DiagnosticReport, DocumentReference, CarePlan, CareTeam, Goal,
Device, ImagingStudy, SupplyDelivery, Coverage, Claim, ExplanationOfBenefit, Provenance.

## Who can see what

Access is decided in the database, per Patient compartment. Four kinds of callers:

| Caller | Identified by | Patient-scoped resources | Reference data (Practitioner, Organization, ...) | Audit log |
|---|---|---|---|---|
| Patient or clinician | rows in `fhir.patient_access` | read or write the granted compartments while the grant is valid; deleting a Patient is admin only | read | no |
| Admin | JWT `app_metadata.fhir_role = 'admin'` | everything | read and write | read |
| Service role | service role key, server side only | bypasses RLS | bypasses RLS | bypasses RLS |
| Anonymous | no session | nothing, not even the schema | nothing | nothing |

Granting access is a row:

```sql
-- a patient portal user sees their own record
insert into fhir.patient_access (user_id, patient_id, access_level, reason)
values ('<auth.users.id>', '<patient id>', 'read', 'patient portal');

-- a clinician covering tonight's shift
insert into fhir.patient_access (user_id, patient_id, access_level, valid_until, reason)
values ('<auth.users.id>', '<patient id>', 'write', now() + interval '12 hours', 'on call');
```

Making someone an admin is a claim in `app_metadata`, which users cannot edit themselves:

```sql
update auth.users
set raw_app_meta_data = raw_app_meta_data || '{"fhir_role": "admin"}'
where email = 'admin@example.com';
```

The same from a server: `supabase.auth.admin.updateUserById(id, { app_metadata: { fhir_role: 'admin' } })`.

Rows without a patient (an Observation with no subject, for example) are visible to admins only.
`fhir.has_patient_access(patient_id, 'write')` is there for your own policies and checks.

## Audit log and history

Writes and access grant changes are audited by triggers, so there is no way around them:

```sql
select occurred_at, action, resource_type, resource_id, actor_id, actor_role, request
from fhir.audit_log
where patient_id = '<patient id>'
order by occurred_at desc;
```

Reads are audited when they go through `fhir.read_resource()` or `fhir.patient_everything()`,
which is what the clients use. A plain `select` through PostgREST is not audited at row level,
because Postgres has no select triggers. For those, use the Supabase API logs or route reads
through the RPCs. The log stores identifiers only, never the resource payload.

History keeps every superseded version, including the last one before a delete:

```sql
select version_id, operation, last_updated, resource
from fhir.history('Patient', '<id>');
```

## FHIR operations and errors

Every operation is a Postgres function, callable as `POST /rest/v1/rpc/<name>` or from SQL.
They run as the signed-in user, so RLS always applies. [docs/api.md](docs/api.md) has the full
contract with `curl` examples; the short version:

| Function | Does |
|---|---|
| `read_resource(resource_type, id)` | returns the resource and logs a read |
| `search_resources(resource_type, patient_id, filters, max_results, skip, newest_first)` | filters on the search columns, logs one search event |
| `log_access(resource_type, resource_id)` | records a read you made through the table API, after checking you may see the row |
| `create_resource(resource)` | inserts and returns the stored resource with `id` and `meta` |
| `update_resource(resource, expected_version)` | full replace; `expected_version` gives optimistic locking (If-Match) |
| `delete_resource(resource_type, id)` | deletes; the last version stays in history |
| `history(resource_type, id)` | every version, newest first |
| `patient_everything(patient_id)` | a Bundle with the whole compartment the caller may see |
| `import_bundle(bundle)` | transaction or batch import: resolves `urn:uuid` and `Type?identifier=` references, honours `ifNoneExist`, upserts by id |

Errors come back with an HTTP status (400, 403, 404, 409) and a FHIR `OperationOutcome` in the
response `details`, so a FHIR library in any language understands them. Not found and not allowed
both answer 404, so ids cannot be enumerated.

## Clients

| Language | Where | Notes |
|---|---|---|
| TypeScript | `packages/typescript/` | `Database` type for supabase-js with `resource` typed per table via `@types/fhir`, and `createFhirClient()` with `read`, `search`, `create`, `update`, `remove`, `history`, `everything`, `importBundle`, `logAccess`. Errors are `FhirError` with `status` and `outcome` |
| NestJS | `examples/nestjs/` | request-scoped `FhirService` built from the `Authorization` header, exception filter mapping `FhirError` to status plus OperationOutcome, a `patients` controller |
| Elysia (Bun) | `examples/elysia/` | the same pattern in 70 lines: `derive` builds the client per request, `onError` maps errors |
| Go | `examples/go/` | standard library. Login, list, audited read, search, error handling |
| Python | `examples/python/` | same flow, standard library; drops into Django or FastAPI |
| PHP | `examples/php/` | same flow, PHP 8.1+ with streams only; drops into Laravel or Symfony |
| Java | `examples/java/` | JDK `HttpClient` plus Jackson, Maven; becomes a Spring bean |
| C# | `examples/csharp/` | .NET 8, `HttpClient` and `System.Text.Json`; register through `IHttpClientFactory` in ASP.NET Core |
| Ruby | `examples/ruby/` | `net/http` and `json`; becomes a Rails service object |
| Others | `docs/api.md` | Generate from OpenAPI, or call the functions from SQL with the user's claims set |

The TypeScript `Database` type merges with your own: `type Database = AppDatabase & FhirDatabase`.

## Synthetic data

The seeds come from the Synthea sample set: 4 patients and the 32 organizations, locations and
practitioners they reference. `bun run db:reset` restores them at any time.

To load more patients, locally or on a hosted project:

```bash
# 1. get bundles: the public sample set, or generate your own with Synthea
curl -L -o synthea.zip https://synthetichealth.github.io/synthea-sample-data/downloads/latest/synthea_sample_data_fhir_latest.zip
mkdir -p data/synthea/fhir && unzip -q synthea.zip -d data/synthea/fhir

# 2. import through fhir.import_bundle with the service role key
SUPABASE_URL=http://127.0.0.1:54321 SUPABASE_SERVICE_ROLE_KEY=... \
  bun run seed:synthea --dir data/synthea/fhir --limit 25
```

`bun run seed:build --dir data/synthea/fhir` regenerates the committed seeds from such a directory.

## Testing

```bash
bun test            # domain and client, no database needed
bun run test:db     # pgTAP against the local database: RLS, triggers, import, API
bun run test:http       # the same guarantees seen from outside, through PostgREST (needs the stack up)
bun run test:examples   # every example in examples/ against the stack (needs the toolchains)
```

The pgTAP suite is the contract: a patient cannot read another compartment, read-only grants
cannot write, expired grants stop working, anonymous gets nothing, `user_metadata` cannot fake an
admin, every write is versioned and audited, log entries cannot be fabricated, a clinician cannot
delete a Patient. The HTTP suite checks that any client sees exactly that (it tests this starter's
contract, not conformance to the FHIR REST specification). CI runs all of it on every push and
runs every example against the stack.

## Use it in your project

**On Supabase**

1. Copy `supabase/migrations/*_fhir_*.sql` into your `supabase/migrations/`, keeping the order
   (or apply `sql/dist/supabase-fhir.sql` as a single migration).
2. Expose the schema: add `"fhir"` to `schemas` under `[api]` in `supabase/config.toml`, and on
   hosted projects under Project Settings > API > Exposed schemas.
3. Run `supabase db push`, insert access rows for your users, set the admin claim for your operators.
4. Pick a client: copy `packages/typescript/src/`, adapt an example, or generate one from OpenAPI.
5. Leave `supabase/seeds/` behind: demo users and synthetic patients are for local development.

**On plain Postgres** (any host, with or without PostgREST)

1. Run `sql/compat/plain-postgres.sql` once as a superuser: it creates the roles and the `auth`
   helpers the policies rely on.
2. Apply `sql/dist/supabase-fhir.sql`.
3. Put PostgREST in front (`db-schemas = fhir`) and issue JWTs yourself, or connect from your
   backend and set the user's claims per transaction as shown in [docs/api.md](docs/api.md).

Need another resource type? One migration line, plus an entry in `TABLE_NAMES` and `ResourceMap`
in `packages/typescript/src/domain/resource-types.ts` if you use the TypeScript client:

```sql
select fhir.define_resource('Specimen');
alter table fhir.specimen
  add column status text generated always as (resource ->> 'status') stored;
```

## How it compares

This is FHIR-shaped storage with access rules and an audit trail inside the database you already
run. It is not a FHIR server.

| | supabase-fhir | Medplum | HAPI FHIR |
|---|---|---|---|
| What it is | schema, RLS, audit and FHIR operations inside Supabase or Postgres | a full FHIR server and platform (REST API, auth, subscriptions, UI) on Postgres | the reference FHIR server, in Java |
| Pick it when | you are already on Supabase and want FHIR data next to the rest of your app, with no extra server to operate | you want a complete FHIR platform and will run it or pay for it | you need maximal specification coverage on a JVM stack |
| FHIR REST API (`GET /Patient/{id}`, search parameters) | no, RPCs and tables; a REST facade is on the roadmap | yes | yes |
| Profile validation | no | yes | yes |
| Access rules | row level security per patient compartment | access policies | interceptors, your code |

## Limits and roadmap

- Not a FHIR server: no `GET /Patient/{id}`, no FHIR search parameters, no profile validation (US Core and friends). The RPCs and tables cover the common operations.
- No SMART on FHIR scopes. Supabase Auth plus `patient_access` covers patient and clinician apps.
- Multi-tenant (one database, many organizations) is planned on top of the compartment model.
- A FHIR REST facade (`GET /fhir/Patient/{id}`, `GET /fhir/Observation?patient=...`) so off-the-shelf
  FHIR SDKs work unchanged is the next milestone (UC-028 in the backlog).
- `_history` and `$everything` are here; `$export` is not.

Compliance note: this project gives you technical controls (isolation, audit, versioning).
HIPAA or PIPEDA compliance also depends on your Supabase plan and BAA, key handling, retention and
process. Talk to your compliance lead before storing real PHI.
